# judge_net 设计文档

> 本文件阐述 judge_net 网络冲突法官智能体的设计哲学、架构决策与黑天鹅奖叙事。
> 面向评审者、维护者与对设计感兴趣的用户。

## 一、问题痛点：网络冲突的"旁观者困境"

互联网降低了表达门槛，也放大了冲突烈度。当一场网络争吵发生时：

- **当事方**陷入"当局者迷"，情绪驱动论证，难以看见自身谬误。
- **旁观者**缺乏对议题的深入认知与对论证结构的分析能力，常被话术带节奏，难以做出公平判断。
- **平台**只管内容合规与否，不评判对错。
- **专业仲裁**（法律、调解）成本高，触达不到日常网络口角。

结果是：大量网络冲突在"各说各话—情绪升级—群体站队—群体性撕裂"的路径上耗散，伤害网络生态与个体心理。

**judge_net 的切入点**：用一个 AI 法官补位"旁观者理性分析"的空缺——不对当事人下道德判决，不对抗平台合规，而是给争议一份结构化、有信源、可上诉的技术性裁决。

## 二、核心设计哲学

### 2.1 网络和谐健康优先于争论输赢

这不是一句口号，而是贯穿设计的硬约束：

- 拒裁清单（`safety_refuselist.md` R1-R6）会主动中止裁决，转介专业资源——因为有些冲突不该被裁决。
- 应答话术模式默认推荐"降温退场"而非"反击升级"。
- 建设性建议是裁决报告的强制节，不能省略。

### 2.2 不各打五十大板

伪装中立是最大的不公正。设计上强制：

- A/E/F 类争议必须给出"较正确一方"判定（事实层面）。
- 价值分歧议题必须显式声明"不裁决对错"，而非模糊处理。
- 回归测试有全局断言：至少一案例出现"较正确一方"，否则判定失败。

### 2.3 不冒充真理裁判

裁决权有边界：

- 价值/审美/道德取向只澄清前提差异，不判对错。
- 不可核实事宜显式写"无法核实"，不装作全知。
- 模型偏见透明声明，敏感议题提示读者。

### 2.4 三层分析框架

争议被拆解为三个正交维度，避免混为一谈：

| 维度 | 处理对象 | 工具 |
|---|---|---|
| 事实层 | 主张是否为真 | `source_credibility.md` 信源分层 |
| 逻辑层 | 论证是否成立 | `fallacy_taxonomy.md` 21 谬误 |
| 情绪修辞层 | 是否用不正当手段 | 6 类修辞战术 |

事实错误不算谬误，情绪本身不是错误——三者各司其职，互不替代。

## 三、架构决策：高代码路线（DIY 高代码赛道）

### 3.1 为什么放弃智谱清言低代码方案改走高代码

最初设计为智谱清言自定义智能体 + 分享链接交付，但在尝试创建时发现：

| 维度 | 智谱清言智能体 | 自建 FastAPI |
|---|---|---|
| 模型选择 | 平台内置固定 | paratera GLM-5.2 + GLM-4V 自由切换 |
| 联网检索 | 平台内置不可控 | 自接 Tavily，信源分层可控 |
| 视觉 OCR | 平台调度的 vision 模型 | paratera GLM-4V 直调 |
| 多轮上诉/话术 | 平台对话记忆黑盒 | 自建 session，TTL 与状态可控 |
| 前端 UX | 平台固定 UI | 自定义 12 节渲染、按钮流程 |
| 自主性 | 受平台模板与工具白名单约束 | 完全自主 |
| 黑天鹅奖导向 | 工程量看似低但实质受限 | 工程可见、可审计、可迭代 |

自主性差异是关键——智谱清言的"通用助手"模板会预设话术偏好，与 judge_net 的中立法官人格冲突；平台搜索与 vision 模型不可控，裁决可信度上限被平台锁死。

### 3.2 高代码架构

```
浏览器（原生 HTML/JS）
  ↓ HTTPS
FastAPI 后端（app/）
  ├─ /v1/adjudicate  主裁决（multipart：文本+截图）
  ├─ /v1/appeal      上诉（局部重审）
  ├─ /v1/reply-script opt-in + 话术生成
  └─ /healthz /readyz
  ↓
核心模块（app/core/）
  ├─ prompt_builder  启动加载 system_prompt.md + 7 个 knowledge/*.md
  ├─ ocr             GLM-4V 截图→JSON（speakers + messages）
  ├─ segmentation    发言方归属启发式
  ├─ search          Tavily + 信源 Tier 分层映射
  ├─ session         内存 dict + TTL 清理（v1 不持久化）
  ├─ llm             AsyncOpenAI + tenacity 重试
  └─ pipeline        编排：OCR→分割→检索→三层分析→报告
  ↓
paratera MaaS（OpenAI 兼容）+ Tavily
  ↓
腾讯云轻量服务器（Docker run + .env + nginx 反代 + 公网域名）
```

### 3.3 部署模式（参考 scholar_agent）

不在仓库里写腾讯云配置文件——所有部署配置在服务器本地，仓库只持有 Dockerfile + .env.example：

1. ssh 到轻量服务器
2. scp 上传代码 或 git clone
3. `cp .env.example .env`，填密钥
4. `docker build -t judge-net .`
5. `docker run -d -p 7860:7860 --env-file .env --restart always judge-net`
6. nginx 反代 7860 到公网域名 + certbot 申请 HTTPS

详见 `deploy/deployment_guide.md`。

### 3.4 提示词即架构（仍成立）

所有业务逻辑仍沉淀在 `system_prompt.md`（558 行）+ `knowledge/*.md`（7 个文件 1181 行）中，由后端 `app/core/prompt_builder.py` 启动时加载注入。后端代码只做编排（OCR、检索、session、HTTP），不做业务判断——这与低代码方案的逻辑一致，只是把"宿主"从智谱清言平台换成自建 FastAPI。

### 3.5 双交付物策略

- **腾讯云轻量服务器公网地址**：评委点链接即用，零门槛。
- **GitHub 仓库**：版本管理提示词、知识库、金标准案例、设计文档、回归脚本、应用代码，体现工程严谨性，便于迭代。

## 四、原始构想的五个环节与拓展

用户原始构想包含五个环节，本设计在各环节上的拓展点如下：

### 4.1 多模态输入（截图 + 文本）

- **原始**：复制对话或上传截图。
- **拓展**：OCR 后强制"预处理摘要"让用户确认发言方归属，避免错认主体；多图按时间拼接去重；剥离 UI 噪声（点赞、表情包、时间戳）。

### 4.2 主题识别与即时研究

- **原始**：搞清事件内容，基于知识储备 + 即时研究。
- **拓展**：议题域名分类（9 类，区分可判对错与价值分歧）；即时研究三件套（权威信源检索 + 信源分层 + 时效标注）；知识截止警示——无信源时显式声明"无法核实"，杜绝幻觉。

### 4.3 冲突形式量级

- **原始**：诚意争辩 / 偶发冲突 / 预谋攻击。
- **拓展**：形式化为 A–F 六类（诚意争辩、偶发口角、CIB 协同造假、营销引流、阴谋论、谣言 AI 骗局），每类对应不同裁决深度与降温路径，附决策树。

### 4.4 三层对话分析

- **原始**：知识信息筛查 + 逻辑问题辨别 + 情绪化输出排查。
- **拓展**：事实层四态（已证实/已证伪/存疑/无法核实，附信源）；逻辑层 21 谬误分类法 + 标注格式；情绪层识别修辞战术（煤气灯、DARVO、关心式钓鱼等）而非贴情绪标签。

### 4.5 特殊形式化解

- **原始**：水军、阴谋论、谣言、AI 化骗局。
- **拓展**：四类特殊情形检测器（CIB 信号、AI 内容信号、阴谋论叙事签名、谣言查无信源），每类有明确触发条件与处理策略；阴谋论走逐条证伪而非陷入"证明不存在"陷阱。

## 五、关键创新点

### 5.1 上诉机制（局部重审）

不同于"再判一次"，judge_net 要求用户指明不服条目 + 提供新证据，只做局部重审，输出"二审备忘录"。这保证了裁决稳定性与可解释性。

### 5.2 应答话术模式（opt-in + 护栏）

双刃剑的平衡：用户须显式 opt-in + 接受 4 条条款；7 类内容绝对禁止生成；5 种风格默认推荐"降温退场"；话术必须基于已核实事实且 ≤300 字。

### 5.3 公众人物阈值

有限度了解的边界形式化：维基百科条目或认证粉丝 >10 万；只调查与争议直接相关的公开信息；禁止调查私生活；非公众人物一律不查。

### 5.4 回归测试

用金标准案例集（5 个匿名化中文社交语境）+ HTTP 集成测试调本地服务，断言 12 节结构 + 关键判定 + 禁止行为，CI 化提示词迭代。回归脚本通过 HTTP 调 `/v1/adjudicate`，与生产路径一致，避免"直接调 LLM 通过但 HTTP 不通"的偏差。

## 六、黑天鹅奖叙事

> 黑天鹅奖鼓励"发现现有应用痛点并进行改造"。

**痛点**：网络争论旁观者缺乏公平判断能力，现有 AI 助手要么回避裁决（"两边都有道理"），要么各打五十大板（伪中立），要么助长对立（给用户写对线话术）。

**改造**：judge_net 不回避裁决——用三层分析框架 + 信源分层 + 谬误分类法，给出有据可查的较正确一方判定；同时以"网络和谐"为最高原则，内置拒裁清单与降温优先策略。

**产品思维**：自建 FastAPI + 原生前端 + Docker 部署，提供公网访问地址；GitHub 仓库开放设计哲学与回归测试，体现可迭代性。架构自主——LLM 选型、检索 API、视觉模型、UX 流程均自己掌握，不被平台锁定。

## 七、局限与未来工作

### 7.1 当前局限

- **联网检索额度**：Tavily 免费 1000 次/月，超出后降级为仅模型知识；批量裁决时需监控额度。
- **OCR 受视觉模型能力限制**：复杂截图（多图拼接、长截图）可能漏识别；GLM-4V 对 UI 噪声剥离效果取决于截图清晰度。
- **会话不持久**：内存 session store，TTL 1 小时，服务器重启即丢失。上诉须在同一会话内完成。
- **回归测试样本量小**：5 个金标准案例覆盖主要类型，但未覆盖所有边界。
- **无鉴权**：v1 公开访问，部署后可能被滥用消耗 API Key 额度。建议加简单 Bearer 鉴权或限流。

### 7.2 未来拓展点

- 接入更多信源（学术数据库、政府公开数据 API）。
- 金标准案例扩充至 20+，覆盖更多边缘情形。
- 多语言支持（英文争议的裁决）。
- 上诉历史的持久化（SQLite/Redis，跨会话二审）。
- 加流式 SSE 输出（前端实时显示生成进度，提升用户体验）。
- 加简单鉴权与限流（防 API Key 滥用）。
- 与平台合规系统联动（CIB 信号自动举报）。
